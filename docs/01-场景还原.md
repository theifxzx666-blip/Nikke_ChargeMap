# 关卡战斗场景还原方案

> 把游戏客户端里的战场资产，还原成一份**可直接做射线求交的三角面集合 + 相机 + 角色锚点**。
> 目标是几何精确，不是画面好看 —— 后续所有段数计算都建立在这份几何上。

- 实现：`数据/build_assembly.py`（装配）、`数据/export_glb.py`（出 glTF）、`数据/viewer/`（three.js 查看器）
- 产物：`数据/导出/assembly_<arena>.json`、`数据/导出/arena_<arena>.glb`

---

## 1. 为什么不能用包围盒近似

早期版本（`build_map.py`）只导出每件物体的 AABB。问题很直接：

| 项 | AABB 近似 | 原生装配 |
|---|---|---|
| 旋转 | 被擦平，物体轮廓变成正立方体 | 保留（Transform 四元数） |
| 子树/斜置件 | 面积暴涨，空隙被填实 | 按真实三角面 |
| 穿透判定 | 擦边就判命中，段数系统性偏高 | 逐个三角面求交 |
| 遮挡判定 | 无法判断「掠过缝隙」 | 可以 |

一件斜放的破车，AABB 会把它正前方 2m 的空气占满 —— 那条缝里本来能穿 2 件。所以必须上真实网格。

## 2. 数据源

| 内容 | 位置 | 说明 |
|---|---|---|
| 资产索引 | `core_store.cdb` | 文件路径 → 偏移/长度，拆包第一步 |
| 战场根 | `SpotSingleMap` | 每张图一个，挂视差分层 `_objectList` |
| 层级 | `Transform` 父链（`m_Father`） | 合成世界矩阵 |
| 几何 | `Mesh.m_VertexData` **或** `m_CompressedMesh` | 见 §3.2 —— **两种都存在，读错就是 0 顶点** |
| 索引 | `Mesh.m_IndexBuffer` | `uint16` |
| 贴图 | `MeshRenderer` → `RuntimeTextureInstanceSetter._sprite` → `Sprite.m_RD.texture` | |
| 材质 | `Material.m_SavedProperties` | `_Color / _FogColor / _FogDensity / _FogGradient` |
| 相机 | `spotcameracontrol` 上的 `Camera` **（可能没有）** | 见 §3.6.1；`fieldOfView 60 / near 0.1 / far 300 / ClearFlags 1` |
| 碰撞档 | **GameObject 根节点名**（`soft` / `medium` / `hard` …） | `CollisionGradeType` 不承载档位，见 §3.5 |

沼泽 / 母鲸八张图的相机参数完全一致（`fov 60, near 0.1, far 300`），说明战场相机是统一机位模板，差异只在锚点。
第 47/48 章的 cityforest 三套**包里没有 `Camera` 对象**，`fov` 沿用 60（详见 §3.6.1）。

## 3. 装配算法

### 3.1 世界矩阵

每个 Transform 给 `(p, q, s)`，按 TRS 合成：

```
M_local = T(p) · R(q) · S(s)          # q 是四元数 (x, y, z, w)，S 的非均匀缩放先作用在旋转前
M_world = M_parent · M_local          # 沿 m_Father 逐级上溯
```

非均匀缩放必须写在旋转**之前**（Unity 的 localScale 是局部轴上的缩放），否则斜置的拉伸件会错位。

### 3.2 网格提取：两种存储，先判再读

**先判断 `m_CompressedMesh` 是否为空**，这是最容易静默失败的一步：

```python
from UnityPy.helpers import MeshHelper

mesh = obj.read()
if mesh.m_CompressedMesh.m_NumVertices > 0:
    m = MeshHelper.MeshHandler(mesh)      # 压缩网格：必须解压
else:
    m = mesh                             # 原生网格：直接读 m_VertexData
assert len(m.m_Vertices) > 0, f"{name} 读出 0 顶点"
```

| 批次 | 存储形态 | 直接读 `m_VertexData` 的结果 |
|---|---|---|
| 沼泽 / 母鲸八套 | 原生 `float32×3`，stride 12 | 正常 |
| **第 47/48 章 cityforest 三套** | **`m_CompressedMesh`** | **0 顶点、0 三角面，且不报错** |

失败形态很隐蔽：装配 JSON 里 props 数量正常（cityforest `001` 有 189 件），
但 `tri` 全是空数组，后续「可破坏物 0 件」看起来像「这关没有可破坏物」。
**必须在装配阶段断言 `总三角面 > 0`。**

实测**所有原生 mesh 都是 0.5 单位厚的平板**，z 只取 `{0.0, 0.5}` 两个值 —— 这是 2D 战场的美术约定，不是巧合。
所以只导出板厚方向一端的那层顶点与三角形：

- 投影后轮廓完全等价；
- 侧壁厚度对屏幕面积的影响 < 1%；
- 数据量减半。

注意「zmin」这个说法只在板正面朝 +z 时成立。cityforest 的板件朝向多变（世界包围盒 z 从 2.69 到 185.6），
要按**局部三向尺度最小的那个轴**判板厚方向，不能硬取世界 z。

顶点先烘焙世界矩阵，再按板厚面过滤，最后重映射索引（`remap`），保证索引不越界。

### 3.3 无网格装饰：Sprite billboard 规则

部分无碰撞装饰只有 `Sprite`、没有 `Mesh`。这类件按运行时规则还原成四边形：

```
wu = sprite.w / sprite.pixelsToUnits
hu = sprite.h / sprite.pixelsToUnits
x0 = -pivotX · wu ,  x1 = (1 - pivotX) · wu     # y 同理
```

**验证**：`sm_building03` 的 sprite 为 215×387，`pixelsToUnits = 100`，Transform 缩放 8 →
`215/100 × 8 = 17.2`、`387/100 × 8 = 30.96`，与原生 AABB `17.2 × 30.96` **完全吻合**。这条规则是实测对上的，不是猜的。

八张沼泽 / 母鲸图里 quad 件占比约 20~40%（`001` 有 135 件 / 442 件）。
**cityforest 三套升到 54%~59%**（`001` 103/189、`002` 72/122、`003` 114/206）——
这批美术更依赖 billboard 拼贴，quad 是主路径而不是补充。

### 3.4 原生 mesh 没有 UV

`Mesh` 只导出了 position，没有 UV 通道。贴图按**正面局部包围盒归一化**映射：

```
u = (x - x0) / (x1 - x0),  v = (y - y0) / (y1 - y0)
```

只在查看器里影响观感，不影响任何几何计算。

### 3.5 分组

**档位只有一个权威来源：物件所在 GameObject 的根节点名。**

| 组 | 语义 | 参与计算 |
|---|---|---|
| `soft` | 软质可破坏物（HP 100） | 命中计数，会碎 |
| `medium` | 中质（HP 500） | 命中计数，会碎 |
| `hard` | 硬质（HP 1000） | 命中计数，会碎 |
| `noncol_object` | 无碰撞装饰（Sprite billboard 为主，占比 30%~60%） | **完全不参与**：不挡、不充能，只进渲染 |
| `static_object` | 静态不可破坏 | **只挡不充能** |
| `ground` | 地面 | **只挡不充能** |
| `cover_object` | 我方掩体（HP 8000） | **不计段数**，且占据像素 |

`cover` 字段记录该件属于哪个掩体（`cover_1`~`cover_5`），用于判断「这是不是我自己的掩体」。

#### 3.5.1 `CollisionGradeType` 不能用来判档位

装配 JSON 里的 `q` 字段是 `CollisionGradeType` 原值。八套实测：

| 组 | `q` |
|---|---|
| soft / medium / hard / static_object / noncol_object | **全部 0** |
| cover_object / ground | −1 |

也就是说它**只区分「可穿 / 不可穿」两类，不区分三档**。
cityforest 三套的 `grade` 字段同样全 0，行为一致。

> `q` 留着做「可穿性」的交叉校验即可，**不要拿它当档位**。

#### 3.5.2 名字里的前后缀也不能判档位

曾有一版文档写「前缀 `dm/dn/df` 大致对应 medium/hard 系美术资源」—— 这是错的。反例（`sbg_cityforest_001`）：

| 物件 | 实际档位 | 为什么是反例 |
|---|---|---|
| `sbg_cityforest_df_tree04_m` | medium | `df` 前缀但只是 medium |
| `sbg_cityforest_dm_structure02_h` | **medium** | `_h` 后缀但不是 hard |
| `sbg_cityforest_df_billboard31_h` | **medium** | `_h` 后缀但不是 hard |
| `sbg_cityforest_dm_crane02_h` | hard | 全套 30 件里唯一的真 hard |

后缀命中率：`_s` → soft 16/16、`_m` → medium 11/13、`_h` → hard **仅 1/3**。
按 `_h` 筛会把两件 medium 当成「耐久 1000、打不碎」。

> 前后缀只是美术命名习惯，**档位只看 root 节点名**。

### 3.6 锚点

`SpotSingleMap` 上挂一组空物体当锚点，全部是**5 个阵位各一份**的数组：

| 锚点 | 含义 | 用法 |
|---|---|---|
| `character_position` | 5 个阵位的角色脚下坐标（y = −2.34） | 枪口 = 该点 + 枪口高 1.45 |
| `cover_1` ~ `cover_5` | 5 个掩体位置 | `cover` 字段归属 + 阵位筛选 |
| `camera_position` | 5 个阵位的相机位置 | 深度图光栅化原点 |
| `aim_position` | 5 个阵位的默认瞄准点 | 只用于初始化视角 |
| `hide_position` | 掩体后躲藏点 | 未使用 |
| `NotCombatZone` | 非战斗区三角标记 | 未使用 |

#### 3.6.1 阵位配对：数组顺序 ≠ 阵位号

锚点是「每个名字下挂一个 Transform 数组」，**数组下标不是阵位号**。
按名字列表 `pop(0)` 顺序取，实测会把 `cover_3` 的 `aim` 配给 `cover_1`。

必须读组件级权威字段 **`NKSpotCover.CoverIndex`** 来配对。

另外城市林地（cityforest）三套的 `anchors` 里多一个 `cover`（单值 `[0, 0, 0]`），三套都有 —— 无实际用途，别当成 `cover_1`。

#### 3.6.2 掩体布局逐图会变，阵位坐标不能跨图套用

| 图 | `cover_object` 五个坐标 |
|---|---|
| `sbg_001` | `(4.31,-2.44,4.9) (-4.23,-2.49,2.9) (-1.206,-2.44,4.9) (1.193,-2.44,2.9) (-5.766,-2.44,4.9)` |
| `sbg_002` | `(-3.25,-2.44,2.9) (2.7,-2.44,2.9) (4.057,-2.552,4.9) (-0.74,-2.569,4.9) (-6.67,-2.44,4.9)` |

同一家族里 `z` 只在 `{2.9, 4.9}` 两档、`y` 基本固定在 −2.44 上下，但 `x` **逐图重排**。

对照：`character_position` 五套完全一致（`(-6.0,-2.34,4.5)` / `(-3.3,-2.34,2.5)` / `(-0.6,-2.34,4.5)` /
`(2.1,-2.34,2.5)` / `(4.8,-2.34,4.5)`）—— 那是**角色站位模板**，可以直接沿用；
掩体位置必须每图实读。

#### 3.6.3 相机与枪口的关系

以 001 为例（第 1 阵位）：角色 `(-6.0, -2.34, 4.5)`、相机 `(-4.8, 0, 0)`、掩体 `(-5.4, 0, 4.9)`。

**相机与枪口的关系**（这是后续算法的关键前提）：

| 方向 | 差值 | 说明 |
|---|---|---|
| 纵深 z | **4.5 m** | 相机在角色身后 |
| 横移 x | **1.2 m** | 相机偏右 |
| 竖直 y | **0.89 m** | 相机在枪口上方（枪口 y = −2.34 + 1.45 = −0.89，相机 y = 0） |

这三条偏移是**阵位模板常量**，8 张沼泽/母鲸图与 3 张 cityforest 图全部一致
（cityforest 三套用 `camera_position − character_position` 反算，同样是 `(1.2, 2.34, −4.5)`）。

`GUN_H = 1.45` 是表现参数（枪口相对脚下的高度），不是配置表里的值。

#### 3.6.4 相机参数的读取分支

| 情况 | 处理 |
|---|---|
| 包内有 `Camera` 组件（沼泽 / 母鲸八套） | 读 `fieldOfView / near / far / clearFlags`，实测 `60 / 0.1 / 300 / 1` |
| **包内没有 `Camera` 组件**（cityforest 三套） | `fov` 取 **60**（与上一条一致），`near/far` 同；`camera` 字段写 `null`，**不要伪造** |
| 相机位置 | 一律取 `camera_position` 锚点世界坐标，不依赖 `Camera` 的 Transform |
| 相机朝向 | 取该 Transform 世界矩阵的三列 |

> **不能用 `aim_position − camera_position` 反推朝向** —— `aim_position` 只是准星点，
> 距相机约 0.1 单位，方向被量化到几乎没有分辨率。

### 3.7 视差分层（结论已降级，别直接外推）

`SpotSingleMap` 分 `Near / Mid / Far / End` 四层。

**八套沼泽 / 母鲸**：`001` 的 442 件里 End 层 422 件、无层归属 20 件，`Near / Far` 全是 0。
其余七套同形。所以在这八张图上「忽略分层」没造成任何误差。

**cityforest 三套**：分层是真在用的。

| 图 | 有层归属 / props | Near | Far | End | 无层 |
|---|---:|---:|---:|---:|---:|
| `sbg_001` | 108 / 189 | 49 | 26 | 33 | 81 |
| `sbg_002` | 65 / 122 | 22 | 13 | 30 | 57 |
| `sbg_003` | 128 / 206 | 49 | 35 | 44 | 78 |

（props 级 `layer` 字段统计，与 `layers` 根节点下的对象计数不等价，两者不要混用。）

#### 3.7.1 「分层不改变世界坐标」这条从来没有被实证过

所有 `layers.*.scrollWidth` 在两批数据里**全部读成 `0.0`** —— 包括沼泽八套。
这更像是**字段没读到**，而不是「确实没有滚动宽度」。

所以正确的表述是三段，不能压成一句：

| 陈述 | 状态 |
|---|---|
| 八套沼泽/母鲸的 props 都在 End 层 | 实测成立 |
| 分层不改变世界坐标 | **未验证**（`scrollWidth` 恒 0） |
| 因此几何计算可忽略分层 | 只在「分层确实无位移」时成立，**不能默认** |

落地要求：`scrollWidth` 读不到就打印 `UNKNOWN`，页面角标写「分层位移未验证」。
**不要用 `0.0` 冒充「确实没位移」。**

验证方法（一条就够）：进游戏同一点位左右拖屏，比对两帧里同一个近景物件的位移量。

### 3.8 雾与后处理

`fog`（`color / density / gradient`）与 `postfx`（`bloom / vignette / colorAdjust`）只写进 viewer 用于还原观感，不参与计算。

### 3.9 地形碰撞网格必须过滤

cityforest 包里有一批以 **`_col`** 结尾的网格（如 `ground_col`）—— 它们是**地形碰撞体，不是可视美术**。

混进三角面集合有两个后果：

1. 渲染时整片糊住画面；
2. 射线在第一米就撞上「隐形地板」，**所有段数归零**，而报错信息只会说「无候选点」。

```python
if name.endswith('_col') or '_col_' in name:
    continue    # 地形碰撞，不参与渲染也不参与求交
```

沼泽 / 母鲸八套没有这批件，所以原实现没有这条过滤 —— 换章节就会踩到。

## 4. 产物与查看器

```
build_assembly.py  →  assembly_<arena>.json   顶格：arena / anchors / layers / props / camera / postfx / fog / materials
export_glb.py      →  arena_<arena>.glb       三角面 + 贴图 + 相机
viewer/index.html  →  自由查看（拖拽相机）
viewer/fp.html     →  玩家视角 + 点位标注（默认取 cover_3 机位）
```

`props[]` 每项字段：

| 字段 | 含义 |
|---|---|
| `n` | 物件名（`sbg_<区域>_<前缀>_<型号>`，前缀 `dm/dn/df` **与档位无关**，见 §3.5.2） |
| `g` | 分组 = root 节点名（见 3.5），**唯一档位来源** |
| `q` | `CollisionGradeType` 原值（只表可穿/不可穿，不表三档，见 §3.5.1） |
| `cover` | 归属掩体（仅 `cover_object`） |
| `layer` | 视差层 |
| `tex` | 贴图名 |
| `m` | 世界原点 |
| `v` | 世界坐标顶点 `[[x,y,z], ...]` |
| `i` | 三角面索引 |
| `lb` | 正面局部包围盒 `[x0, y0, x1, y1]` |
| `uv` | 归一化 UV |
| `quad` / `sprite` | 标记 sprite 生成的四边形 |

### 4.1 cityforest 批次用的是另一套字段名

第 47/48 章那一批（`asm_sbg_00X.json`）字段名不同，跨批次复用工具时必须先做映射：

| 本仓库 | cityforest | 说明 |
|---|---|---|
| `arena` | `scene` | |
| `props[].n` | `props[].name` | |
| `props[].g` | `props[].root` | 语义相同 |
| `props[].q` | `props[].grade` | 两批都全是 0 / null，同样没用 |
| `props[].i` | `props[].tri` | 都存扁平索引 |
| `props[].lb` | `props[].uv`（配 `uvs: "planar"`） | cityforest 不做 bbox 归一化，改平面投影 |
| `props[].quad` | `props[].kind == "quad"` | |
| `camera` | `camera`（`null`） | 见 §3.6.4 |
| `layers.X.n` | `layers.X.n` | cityforest 多一个 `n` 计数 |

**不要直接拿 `data['props'][0]['n']` 这种写法跨批次跑** —— 会静默取到 `None`，然后整批物件无名。

启动：双击仓库根目录的 `启动战场查看器.bat`（起 8899 静态服务并打开页面）。

## 5. 精度校验

还原是否可信，不能靠肉眼看画面。`audit_px.py` 的 **A 项**做了往返自洽：

```
像素 (u,v) → 相机射线 → 世界交点 P
P → 相机空间 → 投影 → 像素 (u',v')
|u−u'| 、|v−v'| 应趋近 0
```

八张图 130 个点位实测：**`err_max = 0.02~0.03 px`**，命中点到射线的垂距 `< 0.06 m`（阈值 0.2 m）。

这说明「世界矩阵合成 → 三角形 → 投影 → 反投影」整条链路没有代数错误。误差来源只剩相机参数标定（见下）。

## 6. 已知近似与误差

| 项 | 处理 | 影响 |
|---|---|---|
| 0.5 厚侧壁 | 丢弃，只留正面 | 屏幕面积 < 1% |
| 原生无 UV | 按 bbox 归一化 | 仅观感 |
| 超大远景件 | `MAX_SPAN = 60 m` 以上丢弃 | 不可能是判定点（屏幕上只有几像素） |
| 相机俯角 | **未标定**，假定 0° | 2° 俯角 ≈ 27 px 系统性偏差（P0 待办） |
| 相机 FOV | 取 `Camera.fieldOfView = 60`（纵向）；无 `Camera` 对象时同样取 60 | ±0.8° → 5 px；宽高比变化影响见 `03-实例.md` |
| 敌人 / 队友 / 残骸 | **完全未建模** | 实战中遮挡打折，幅度与站位相关 |
| 动态物件（可破坏物碎后） | 视为整体移除，无残骸 | 与实机存在偏差 |
| 视差分层位移 | **未验证**（`scrollWidth` 恒 0，字段可能没读到） | 见 §3.7.1；cityforest 三套 Near 层占 45%~50%，不再是可忽略量 |
| `*_col` 地形碰撞网格 | 过滤掉 | 漏过会让射线撞隐形地板，段数全归零（§3.9） |
| 压缩网格 | 走 `MeshHelper.MeshHandler` | 漏过会得到 0 顶点空装配，且不报错（§3.2） |
| 跨批次 schema | 两批字段名不通用 | 直接复用会静默取到 `None`（§4.1） |

**相机俯角是全链路唯一的系统性不确定项**。它不影响「这个方向能穿几段」，只影响「红点标在哪个像素」—— 但它决定了所有页面上的像素坐标是否可信。这一点在 `02-充能点算法.md` 的审计一节里有量化。

> 2026-10-26 补充：如果把**角度（yaw/pitch）当作一级产物、像素当作派生**，那么俯角误差只污染标注、不污染选点结论 —— 能把这一项从「全链路不确定」降级为「仅标注不确定」。详见 `04-跨章节对照.md` §5。
