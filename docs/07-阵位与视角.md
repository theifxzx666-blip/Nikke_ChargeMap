# 阵位（机位）与视角：为什么之前换掩体图不变

> 相关页面：[`H35沼泽丛林玩家视角充能点.html`](../H35沼泽丛林玩家视角充能点.html)
> 相关数据：`数据/导出/px_<arena>_cover_<N>.json`、`audit_<arena>_cover_<N>.json`
> 出图：`数据/render/fp_<arena>_cover_<N>.webp`

---

## 0 问题是什么

页面顶部原本有两个切换条：「点位数量」和「我的掩体」。用户反馈：

> 即使选了点位数量和掩体，实际上图片上并不会发生变化。
> 而且游戏里玩家默认进去是固定 3 号位掩体，不同掩体看到的地图视角是不一样的。

这两句都是对的，而且是同一个缺陷的两面。

---

## 1 四个根因

前三条是「换掩体视角不对」，**第四条才是「图上的点位永远不动」** —— 它是第二轮才暴露的，
而且前三修完也治不好它。

| # | 位置 | 问题 |
|---|---|---|
| 1 | `scan_px.py:273` | `view = "cover_3" if "cover_3" in orgs else sorted(orgs)[0]` —— **机位写死成 3 号位**。整份 `px_*.json` 的像素坐标、可达角度、点位集合都只对 3 号位成立 |
| 2 | `gen_fp_page.py` 的 `pick(k)` | 「我的掩体」只做两件事：给表格里 `c1~c5` 那一列加高亮、按该列段数重排行。**它压根没碰图片** |
| 3 | `render/` | 每个战场只有**一张**静态图（`fp_001.png`），本来就是 3 号位拍的。换掩体时没有第二张图可换 |
| 4 | `viewer/fp.html` 的 `drawPoints()` | 点位是 three.js 的 **sprite**（`dotSprite` / `labelSprite`）画在 WebGL canvas 里的。截图那一瞬间就**烧成像素**了 —— `<img>` 不认识 DOM，页面怎么切它都不会变 |

所以「选点位数量 / 选掩体 → 图不变」有两层原因：数据只有一套（1~3），
而**点位被烘进位图**（4）意味着哪怕数据齐全，前端也没有任何手段重绘它。

---

## 1.5 修法：图归图，点归点

```
以前：  场景 + sprite 标注   ──截图──▶  fp_001_cover_3.webp（点位是像素，改不动）
现在：  场景           ──截图──▶  fp_001_cover_3.webp（纯场景）
        点位（px 坐标）──CSS%──▶  <div class="dmk"><i class="dm" style="left:50.9%;top:41.5%">
```

具体三步：

1. **出图关标注**：`fp.html` 新增 `dots=0`（不画 sprite）与 `nodata=1`（不读 `px_*.json`，
   相机改从 `slots.json` 取）。`render_views.py` 出图 URL 带上这两个参数，
   所以**重拍图不会被正在重算的 json 卡住**。
2. **页面画标注**：`gen_fp_page.py` 的 `mark_html(d)` 把每个点的 `px`（1600×900 基准的屏幕像素）
   换算成百分比，输出绝对定位的 `<i class="dm">`。图片按 `width:100%` 显示，百分比自动跟随缩放。
3. **复用现有筛选**：
   - `data-no` → 现有的 `apply(n)` 直接按编号过滤，不用新写逻辑；
   - `data-ss`（该点在 c1~c5 各阵位的稳态段数）→ `pick(k)` 里加一段，`0` 标 `.off`（灰+划掉）、
     `<2` 标 `.faint`（半透明）。

颜色按稳态段数分档：**5+ 金 / 4 薄荷 / 3 蓝 / 2 灰 / <2 暗**，鼠标悬停出该点的
编号、稳态/首轮段数、首击距离、c1~c5 各阵位段数。

## 2 阵位到底差多少（拆包实测）

`导出/slots.json` 里每个战场都有 5 个阵位预制体，**所有战场共用同一套布局**
（root x = ±5.40 / ±2.70 / 0.00，z = 0 / −2.00）：

| 阵位 | 相机 `camera_position` | 角色 `character_position` | 相对 3 号位横移 |
|---|---|---|---:|
| cover_1 | (−4.8, 0.0, 0.0) | (−6.0, −2.34, 4.5) | −5.4 m |
| cover_2 | (−2.1, 0.0, −2.0) | (−3.3, −2.34, 2.5) | −2.7 m |
| **cover_3** | **(0.6, 0.0, 0.0)** | **(−0.6, −2.34, 4.5)** | **0（游戏进图默认）** |
| cover_4 | (3.3, 0.0, −2.0) | (2.1, −2.34, 2.5) | +2.7 m |
| cover_5 | (6.0, 0.0, 0.0) | (4.8, −2.34, 4.5) | +5.4 m |

相机横跨 **10.8 m**、纵深差 **2 m**。FOV 60° 下，10.8m 的横移在 20m 目标上就是 **±15° 的方位差** ——
足以把屏幕中线的目标推到画面边缘，也足以让原本被掩体挡住的一条走廊露出来。

因此**不能只换图、不换点**：像素坐标是「相机射线打到的那个像素」，
相机一动，同一个瞄准角对应的像素就完全不同。反过来，也只有重新选点才知道
「站在这个阵位上还能打哪几个点」。

## 3 现在的做法

```bash
cd 数据
# 单个阵位（默认仍是 cover_3，兼容旧流程）
python scan_px.py 001 --view=cover_3
# 全链路：选点 → 可信度 → 审计 → 轮换，四步都要带同一个 --view
python verify_px.py 001 --view=cover_3 --sim=300
python audit_px.py  001 --view=cover_3
python sim_charge.py 001 --view=cover_3
```

产物命名：

```
导出/px_<arena>_<view>.json      点位（像素 / 角度 / 穿透链 / 各阵位段数）
导出/audit_<arena>_<view>.json   六项独立审计 + 容错锥
render/fp_<arena>_<view>.webp    该阵位的相机出图（**纯场景，不含点位**）
```

`view` 为 `cover_3` 时额外写一份 `px_<arena>.json`，旧脚本不用改。
批量跑（组间并行，12 核上 6 路约 15 分钟；断点续跑，已完成的组自动跳过）：

```bash
python batch_views.py --jobs=6        # 35 章 7 张战场 × 5 阵位
python render_views.py                # 每阵位出图 → webp（dots=0 & hud=0 & nodata=1）
```

> `render_views.py` 会检查 PNG 是否 <200KB 判空白（相机没定位 / glb 没加载）。
> 这次踩过：`slots.json` 里 `camera_position` 是 `[[x,y,z]]` 带一层数组，
> 直接取 `C[0]` 会让相机变 NaN，出来一整张灰图但脚本"成功" —— 现在会直接报错。

页面上新增「机位 · 我站的掩体」切换条（快捷键 Q / W / E / R / T），
**默认停在 3 号位**（游戏进图位置），切换时图、点位表、达标点数、锥宽一起换。
原来的「我的掩体」改名为「跨阵位对照」，含义保留：同一个瞄准点在其它阵位还能打几段。

图上的圆点跟着两个切换条一起变 —— 它不是图的一部分，是 DOM 叠加层（见 §1.5）：
切「显示几个」圆点增减，切「跨阵位对照」打不到的点变灰划掉，切机位整套换掉。

## 5 已知限制

- **朝向仍然固定沿 +z、俯仰 0°**。拆包里 5 个阵位的 `root_quat` 全是 identity，
  所以这是实测值而不是假设；但如果实战里玩家能左右拖镜头，那就多一维自由度，像素坐标要再加一层偏移。
- **审计节和跨战场对照表仍按 3 号位统计**（容错锥必须绑定一个相机位置才有定义）。
  每个阵位自己的锥宽在各自表格里。
- 变阵位时的**动画位移**没建模 —— 按「瞬间站定」处理。
- 各阵位的可破坏物池子是同一批（受击物不随阵位变化），变的只是「能不能打到」。
