# NIKKE 地图充能点计算

从 NIKKE 客户端拆包，还原战场原生装配，按实机相机逐像素反推「一枪能穿几个可破坏物件」，
输出玩家视角的充能点标注页。

目前覆盖 **四批共 18 套战场**，已入库 16 套（cityforest 三套未入场景库，方法见 `docs/04`）：

| 区域 | 章节 | 战场 | 页面（`正式产物/页面/`） | 精度 |
|---|---|---|---|---:|
| 沼泽丛林 `swamplandjungle` | **第 35 章** | `sbg_001`~`005` + boss `bbg008` / `bbg009` | `H35沼泽丛林玩家视角充能点.html` | ±1 px 级 |
| 晶化城市森林 `cityforestundercrystal` | **第 34 章** | `sbg_cityforestundercrystal_001`~`005`（`c001`~`c005`） | `H34晶化城市森林玩家视角充能点.html` | ±1 px 级 |
| 母鲸领域 `motherwhalefield` | 第 39 章（H39-40） | `sbg_mw001`~`003` | `H39-40母鲸领域充能点.html` | ±1 px 级 |

## 结论摘要

### 第 35 章 · 沼泽丛林（63 点）

- 七张战场（5 常规 + 2 boss）全部按**修复后的几何**重算。`z=zmin` bug 修掉后三角面涨 4 倍（001：15,276 → 62,070），
  旧值 130 个点是几何缺口让射线从侧壁穿过去造成的**虚高**，正确值是 **63**。
- 分级 **S 3 / A 2 / B 19 / C 14 / D 25**：001 → 12（最高 4 段，锥中位 4.3px）· 002 → 21（4 段，2.6px）·
  003 → 15（4 段，5.0px）· 004 → 6（2 段，11.1px）· 005 → 9（4 段，1.8px）。
- **圣甲虫 boss**：`bbg008` 受击体 28 件但全画面**没有任何 ≥2 段的共线** → **0 个达标点**，这张图只能打敌人本体充能；
  `bbg009` 受击体 74 件、**6 个达标点**，最高 4 段 `px(242,349)`（50.2m，五阵位全可用），分级 S0 / A1 / B4 / C0 / D1。
- 像素坐标同样只在 16:9 有效。
- **5 个阵位（掩体）全部单独重算过**：c1 **73** / c2 **41** / c3 **69**（游戏进图默认，上表就是这一列）/ c4 **46** / c5 **77** 个点，
  35 组求和 **306**。差得最狠的是 002：2 号位只有 14 个、1/5 号位各 24 个；
  `bbg008` 的 c1~c3 **一个达标点都没有**。逐组对表见 [`docs/07-阵位与视角.md`](docs/07-阵位与视角.md) §4。

### 第 34 章 · 晶化城市森林（120 点）

- 分级 **S 4 / A 7 / B 32 / C 17 / D 60**，锥宽中位 **2.8px**，五图池子 **132%~154%**。
- 最硬的结论仍是**段数与稳定性互斥**：五张图的受击体排成 45~55m 细长队列，共线走廊投到屏幕上只有 1~2px 宽。
  每图因此给了**双榜** —— 段数冠军（理论最优，多数按不住）与实战冠军（锥宽 ≥3px 前提下段数最高）。

### 母鲸领域（3 套，旧几何未回归）

点位与分级仍是 `z=zmin` 修复**之前**的值（本地没有 `sbg_mw*` 原始 bundle，无法重跑）。
现状可用但段数偏低，重跑后应普遍上移 —— **这三套数字不要和其他两批横向比较**。

```
沼泽丛林 35 章  63 点（3 号位；5 阵位合计 306）  S3  A2  B19 C14 D25   锥宽中位 1.8~11.1px（分图）
晶化城市 34 章 120 点（单阵位）                 S4  A7  B32 C17 D60   锥宽中位 2.8px
```

cityforest 三套不能套用上面的分级：可破坏物只有 10~30 件（35/34 章是 63~220 件）、
`hard` 各只有 1 件，池子/需求比大概率 < 30%，**充能点价值本来就低**。

具体推导见 [`PROMPT.md`](PROMPT.md)（§15 像素级选点 / §16 可信度 / §17 战场轮换 / §18 独立审计 / §19 跨章节对照）。

## 重新生成

**一律在工位根执行，不 `cd` 进子目录** —— 路径由 `工具/paths.py` 裁决。

```bash
PY=/c/Users/Administrator/.workbuddy/binaries/python/envs/default/Scripts/python

# 0) 两道闸门，任一非 0 就别往下走
$PY 工具/paths.py --check                # 16 场景件齐不齐
$PY 工具/校验/gen_catalog.py --check     # 表与数据一致否（顺带重生成三张表单）

# 1) 采集（连手机；全量 174 个场景的分级见 docs/11）
$PY 工具/采集/collect_all.py --preflight              # catalog / cdb.idx / zstandard / adb
$PY 工具/采集/collect_all.py --list --tier 1,2          # 看全集与已采状态
$PY 工具/采集/collect_all.py --run --tier 1,2           # 采集 P1+P2（adb 串行，别开并行）
#    它内部已经串好 extract → 装配 → 贴图 → glb → 阵位 → 回填，不用手动分步；
#    要单步调试再用：build_assembly.py → dump_tex.py → export_glb.py（贴图必须早于 glb）

# 2) 四阶段分析（scan → verify → audit → rotate），写 分析/<章节>/<arena>/
$PY 工具/分析/analyze.py 001              # 默认 cover_3 = 游戏进图位置
$PY 工具/分析/analyze.py 001 --view 4     # 指定阵位
$PY 工具/分析/analyze.py --jobs 6         # 全场景全阵位并行；几何指纹未变的自动跳过
$PY 工具/分析/analyze.py --schema         # 只读校验：字段 / 行数 / 指纹是否过期

# 3) 出图 / 出页 / 验收
$PY 工具/出图/render_views.py --force
$PY 工具/出页/gen_fp_page.py && $PY 工具/出页/gen_cf_page.py && $PY 工具/出页/gen_mw_page.py
node 工具/校验/check_page_marks.mjs       # 真机验证：点按钮后圆点数量 / 打灰 / 机位是否真的变了
```

> `analyze.py` 的四阶段顺序是硬编码的，**不要手动拆开跑**。历史上 `verify_px.py` 会整份重写
> `px_*.json`，排在 `sim_charge.py` 之后会把轮换结果冲掉（c005 踩过一次）；现在 `rotate` 固定在最后。
>
> 图里**不带**点位标注 —— 标注是页面上的 `.dmk` 叠加层，按 `px` 百分比定位。
> 之所以这么做：早期把 three.js 的 sprite 截图烘进 webp，页面上切「显示几个」和
> 「跨阵位对照」时图片一动不动（像素不认识 DOM）。详见 `docs/07-阵位与视角.md` §1.5。

单次四阶段实测耗时（`bbg008` / `cover_4` / 16,792 三角面）：约 **4.4 秒**。
全量 16 场景 × 5 阵位在 6 路并行下约 3 分钟。逐阶段数字见 `docs/10-存储规范与场景库.md` §6。

依赖：`numpy`、`UnityPy`（拆包）、`Pillow`（出图）、`openpyxl`（xlsx 表单）。

**换章节前必查五条**（详见 `docs/04-跨章节对照.md` §3）：

```
① 三角面 / 顶点 比值 ≥ 1.5     → 实测全取 1.88、只取一层 0.91。低于 1.5 就是踩了 z=zmin 过滤
                                  （侧壁被丢，三角形只剩 24.5%）；2026-10-26 已默认关闭，
                                  需要时 SHEET_ONLY=1 才启用
② 有没有 *_col 地形碰撞网格     → 有就过滤，否则射线撞隐形地板，段数全归零
③ 包里有没有 Camera 对象         → 没有就用锚点位置 + fov 60，camera 字段写 null
④ 档位来源是不是 root 节点名     → 不是 CollisionGradeType，也不是文件名前后缀
⑤ alpha 该走 MASK 还是 BLEND    → 按不透明像素占比分流（≥50% 走 MASK，否则 BLEND）。
                                  一律 MASK 会把 `*_fog01` 雾片糊成灰块（alpha 均值 0.16、86% 像素 <128）
```

第 ① 条是唯一会**算错数**的：cityforest 三套上它把三角形从 15,614 砍到 3,968（只剩 25.4%），
而日志一切正常。修复后与独立实现逐项一致。

## 已知未解决

- **关卡 → 战斗场景的映射不在客户端**。`CampaignChapterTable` 只给章节所属区域（35 章 = `fcbg_swamplandjungle_001`、
  34 章 = `fcbg_cityforestcrystal_007`），`CampaignStageTable` 只有服务端下发的 `spot_id`，
  `campaignlevelmapgroup_*` 的 MonoBehaviour 里也只有 `_stageId` 和坐标。
  所以只能确定「这一章有这么几张图」，具体哪一关用哪张背景要开背景人工认。
- **母鲸三套还是 `z=zmin` 修复前的几何**（本地无 `sbg_mw*` 原始 bundle）→ 重跑时三角面会涨 3~4 倍，段数会上移，需抽查 Top1
- **光照 / 阴影 / 后处理（bloom、vignette、colorAdjust）没有重建** → 三维视图是「贴图原色 + 均匀增益」，
  不是游戏最终成像，颜色只能作参考
- `_nf_*` 近远景背景卡在游戏里走视差滚动，静态放置会露硬边 —— 当前最明显的观感缺陷（`BG_SKIP=1` 可跳过但画面偏空）
- 天空盒只有 side / upper / under 三张，贴球面会极点拉伸
- 相机俯角 / FOV 未标定 → 像素坐标带 ±27px 系统性不确定
- `hpdamage_limit=30` 语义未定 → 轮换模型 A/B 假设差 1 倍
- 敌人 / 队友 / 残骸的实体遮挡未计（不在场景装配里）
- 单发伤害未拆出，换弹未计
- 视差分层位移未验证（`layers.*.scrollWidth` 两批 11 套全部读成 0.0，疑似字段没读到）
- 同场景内同名的可破坏物会被误并成同一件（用 `name` 判同一性）
- 镜头能否左右拖未确认；若能拖，像素坐标系还要多一维自由度
- **第 34 章目前仍是单阵位**（只有 `cover_3`）→ 其余 4 个掩体的点位尚未算，
  跑一遍 `$PY 工具/分析/analyze.py --jobs 6` 即可补齐（约 15 分钟，已算的会自动跳过）
- **母鲸 3 套 `status: 待补`** —— `mwbmf` 只有几何没有阵位（缺 `slots.json`），另外两套阵位也是老的
- **`001~005` 各有一份重复 bundle**（场景目录里的 `sbg_*` 与共享的 `spotbackground(hd)_*` 同 sha1），
  未删原件。去重可省约 36 MB，但会动到 `source/`，暂不动
- 35 章受击体排成 45~55m 细长队列，共线走廊在屏幕上只有 1~2px 宽 —— 这是「段数高的点按不住」的根因，
  靠算法消不掉，只能靠站点选择绕开（34 章同样如此，锥宽中位 2.8px）

## 下一步（网页工具路线）

理想态是「打开一个网页 → 选场景 → 看每个掩体的充能点」。分三期，**不做无法兑现的承诺**：

| 期 | 内容 | 状态 |
|---|---|---|
| **P1** | 本地跑 `analyze.py` 生成点位资源（本期已具备：四阶段 + 几何指纹 + 表单） | ✅ 可用 |
| **P2** | 网页读「场景库 + 点位资源」，纯前端渲染，支持阵位切换 / 显示点数 / 跨阵位对照 | ✅ 已有雏形（`正式产物/页面/` 三张 + `工具/viewer/fp.html`） |
| **P3** | 浏览器内直接跑分析（WebGPU / WASM） | ❌ **明确不承诺** |

P3 不做的理由：单场景 62,070 三角面 × 7.7 万射线 × 5 阵位 × 300 次扰动，移动端必然 OOM。
真要在线算，也只能是「服务端算 + 前端读」，那就不叫网页工具了，叫接口。详见 `PROMPT.md` §20.6。
