### 1. 天空 —— 最严重，105/112 场景根本没有天空

### 4. 中景横贯全屏的硬直线

- 染色调试（`?gnddbg=1` 染绿地面 / `?nfdbg=1` 染红远景板）确认：是**地面带远端边缘**（只铺到 z≈80 m），

## 修复：双击 `启动场景查看器.bat` 满屏「不是内部或外部命令」

### 根因（三层，全在批处理文件本身，与 python/路径无关）
1. 原 `.bat` 存盘为 **UTF-8 无 BOM + LF**。cmd 按 **CRLF** 解析批处理，纯 LF 且含多字节中文时读取指针错位，
   把中文字节当命令执行 → `'‖' / '棋键镶 ǚ 瀵崇 2cd' 不是内部或外部命令`
2. 文件里 `chcp 65001` 写在中文行**之前**。cmd 有个已知缺陷：批处理中途改代码页会让文件读取位置错乱，
   后面的行被切成碎片 → `'not' 不是内部或外部命令`、`'PY*' 不是内部或外部命令`
3. 于是 `set "PY=…"` 没生效、`%~dp0` 被切碎，最终 python 收到残片 →
   `can't open file 'D:\Codex\Nikke\Nikke_ChargeMap\=D'`（`[Errno 22] invalid argument`）

### 修法（铁律：**.bat 只放纯 ASCII + CRLF，中文路径一律挪进 .py**）
- 新增 **`viewer.py`**（仓库根，ASCII 名）：`runpy.run_path("工具/viewer/serve.py")`，把中文路径留在 Python 侧
- 新增 **`pages.py`**（仓库根，ASCII 名）：静态页服务（8899）+ 依次打开 `正式产物/页面/` 下三张充能图。
  用于替换那个已失效的旧 `启动战场查看器.bat`（原先指向的 `战场示意图\H35…html` 早已迁移）
- 两个 `.bat` 重写为 **纯 ASCII + CRLF、无 `chcp`**，用 `where py` → `where python` 找解释器
- 中文提示语交给 Python 打印（Windows 下走 `WriteConsoleW`，cp936 控制台也不会乱码）

### 验证
`cmd /c "启动场景查看器.bat --no-open --port 8932"` → 零报错，`/工具/viewer/app.html` 返回 **200**；
`xxd` 确认 `0d 0a` 行尾、全 ASCII；`py_compile` 通过；测试进程已清理

### 教训
以后凡是要写 `.bat`／`.cmd`：**只要文件里出现一个非 ASCII 字符，就必须按 GBK 存盘**。
更稳的做法是彻底别在批处理里写中文——`echo` 也交给 Python。

## §22（v17）：画幅 / 机位标定 / 地面接缝 / 贴图完整性

### 已定位并落地的三条

**1. 画幅（真 bug）** —— `app.html` 的 `#c{width:100%;height:100%}` 让画布铺满 stage，
宽高比跟着窗口走，所以「连 16:9 都没有」。改成按 AR 等比内切 + 居中，画布锁死。
- 纵向 FOV 60°（Unity 语义）固定，宽屏只横向扩：16:9=91.49°、21:9=106.83°
- 出图纵向固定 1080，宽度 = round(1080×AR)；21:9 → **2520×1080**
- 21:9 落 `正式产物/场景图/实预图_21x9/`，与 16:9 分目录
- `paths.reel(arena,v,ar)` / `scene_reel.py --ar=21:9`
- 导出尺寸改取 **画布显示尺寸**，不是 stage 尺寸（否则导出的取景≠屏幕上的取景）

**2. 地面接缝（根因是 UV 尺度）** —— 实测 `arena_cf001.glb` 的 `GROUND`（18 顶点/16 面）：
顶点 UV **u 0→6、v 0→5**，即作者已按 6×5 排瓦片（320m/6=53.33m、100m/5=20m）。
旧版 `fixGround` 把 UV 改写成「世界坐标/GTILE(10m)」，**瓦片密度翻 5.3 倍** → 接缝翻 5 倍。
- 改回原生 UV；`GTILE` 只在 `?gnd=world` 保留作对照
- 地面贴图是内嵌的 `ground_tile`（983×390，非 2 的幂，程序合成）：**S 向环绕差 5.46 / 内部仅 1.19（4.6 倍）**，T 向 **0.00**
- 所以横向必须 `MirroredRepeatWrapping`，纵向 `RepeatWrapping`

**3. 贴图空白（推翻旧结论）** —— `工具/校验/audit_mesh_tex.py` 全量扫 112 个 glb：
**13684 张图片全部 `bufferView` 内嵌，外部 uri = 0**，坏引用 0、缺文件 0、无贴图材质仅 2。
→ 「少贴图变空白」**不可能是缺文件**。旧的 `check_tex_refs.py` 校验的是 `images[].uri → tex/`，
而 uri 数为 0，**等于空转**，它的「13684 张 0 缺失」是伪证据。真因只可能是：材质无贴图（纯色板）、
贴图近黑（unlit 无光照 → 死黑，gd001 上半屏）、alphaMode 处理。

### 机位「偏后」：只能标定，不能猜

  改它必须有用户对照结论，**不擅自改**

## §24 四项收尾定案 + 「空白」查到底（v18）

### 一、21:9 HUD 重排问题 → 有硬答案，不重排
从 `spotpresentationbase` 里另挖出两个此前漏掉的资产 `canvas(screenspace-camera)-one|two`，
两份**逐字段完全一致**，含 `CanvasScaler`：
- `m_UiScaleMode=1`（ScaleWithScreenSize）、`m_ScreenMatchMode=1`（**Expand**）
- `m_ReferenceResolution=(1080,1920)`、`m_MatchWidthOrHeight=0`（Expand 下不生效）
- `UISpotCanvas.PlaneDistance=4.3`

Expand 语义 → `scaleFactor = min(W/1080, H/1920) = H/1920`：
16:9 与 21:9 **都是 0.5625**，逻辑画布 3413×1920 → 4480×1920。
**高度锁 1920、宽度随画幅变宽 = UI 元素尺寸恒定、只左右多出空间**。
所以「21:9 横向扩视野」与游戏自己的 UI 语义同向，不存在错配。

### 二~四、另三项
- `UseAutoModeCamera = 0` → 自动机位**当前配置就不激活**，手动战斗走 arenacamera(priority 8)
- `m_BindingMode=1` → Cinemachine `LockToTargetWithWorldUp`（库枚举，**不是**二进制反编）
- `AimStartPosition1..5` 值域 ±0.25/±0.125，「相对全宽 or 半宽」**无证据** → 不推导角度

全部写进 `camera_params.json` 的 `结论[]`，每条带**证据强度**：
`资源实证` > `库语义` > `推导` > `未定`。铁律：不许把库语义写成资源实证。

## §25 事故：对照实验做对了，结论没落地（实预图 112×2 全废）

### 事故链
1. 解 PC 客户端拿到 prefab 旋转（yaw −38.62）→ 写进 `fp.html` **作默认值**
2. 同日做 4 组实渲染对照，**自己判定 yaw=−38.6 会左半屏死灰，只有 yaw=0 对**
3. 落地时**只加了 `?yaw=` 传参能力，没改默认值**，`scene_reel.py` 的 URL 里也没有 yaw
4. → 全量重出的 112 张（16:9+21:9）全走了被否掉的 −38.6
5. 用户一句「现在实预图都是搓的」暴露

### 根因
把「实验结论」和「默认值/出图参数」当成两件事，中间没有强制绑定。

### 修复（两处缺一不可）
- `fp.html`：默认 `YAW = 0`，注释改成实渲染判定 + 写明这次返工

  → 出图脚本从此**不许吃页面默认值**

### 顺带查清的机位物理含义（这次才真正搞懂）
`cover_3` 子树实测：
```
cover_3                z=+4.900
  character_position   (-0.600, -2.340, -0.400)
  camera_position      ( 0.600,  0.000, -4.900)
    aim_position / hide_position
  cover_object         (-1.206, -2.440, 0)   ← 掩体
```
- 相机 world y=0，角色 world y=−2.34，水平间距 **4.66 m** → 角色在相机下方 **26.68°**
- `AimPositionInitOffsetHeight=200px` = 中心下方 12.07°
- 两者相减 = **14.61°** 相机俯角；取 12.3° 时角色在中心下方约 250 px，仍在下三分之一 → 构图成立
- 所以 `yaw=0, pitch=+12.3` = 「站在角色身后 4.66 m、头顶上方 2.34 m，略低头看前方」

## 21:40 俯角重定（第三次返工，PROMPT §26）

**用户**：「现在跟游戏里，战斗开始时，看到的视角差别很大，每个掩体位看到的都是如此」

### 定位过程（这次先让它可测）
1. 加 `fp.html?ghost=1` 调试开关：在 `character_position` 画 1.8m 人形线框 + 脚底圆环（depthTest 关），
   正式出图不传。**纯场景图没有任何参照物，俯角对不对全靠感觉，这是当时反复返工的根因。**
2. 有占位后扫俯角，问题立刻可量化：
   - pitch=12.3（旧）→ 脚底落 72%，脚下空 28% 纯地面 → 「像站在后面看」
   - pitch=auto(87%) → 脚底 87%，角色压在下部
   - pitch=0 → 93.5%

### 12.3° 为什么错（三处，§25.4 整套作废）
1. 减法方向反：命中 200px 折 12.07°，若准星在中心上方，画面中心应更**低**，该加不该减
2. 前提无据：「准星指向角色」纯属假设；`aim_position` 相对相机只偏 (−0.1,0,−0.1)，与角色无关
3. **物理上就不成立**：相机 y=0、脚底 y=−2.34、身高 1.8 → 头顶 y=−0.54，
   **相机只比头顶高 0.10m = 平视**，不可能低头 12°。单这一条就够否掉。

### 新方案：不给角度，给落点
> 约束改成「角色脚底落在画面纵向 f=0.87」，反解俯角（透视精确解）：
> `tan p = (dy − T·h)/(h + T·dy)`，`T=(2f−1)·tan(vfov/2)`

- 112/112 场景解得 **3.54°**（111 个 h=4.657/dy=2.340 同构）
- `ocebg001001` 是另一套 spot 预制体（h=6.322 / dy=3.176），dy/h 比例相同 → 同角，auto 自动兜住

### 落地三处（延续 §25.5 铁律）
| 位置 | 改动 |
|---|---|
| `fp.html` | `pitch` 缺省 `auto`，读 `SC.character_position` 现解；新增 `foot`（缺省 0.87）；兜底 3.54 而非 12.3 |
| `camera_params.json` | `chosen_pitch_deg=3.54` / `pitch_mode=auto` / `foot_screen_y=0.87`；旧 12.07 标「已证伪」 |
| `scene_reel.py` | `cam_pose()` 返回 `(yaw,"auto",foot)`，URL 显式带 `&pitch=auto&foot=0.87` |

`cam_pose()` 返回值特意改成字符串：`pitch_mode` 一旦被改回常数，异形场景立刻失真，
`"auto"` 让「逐场景反解」成为默认路径而非可选项。

### 新铁律（§26.5）
> 凡只能靠标定得到的参数，把标定物换成**可度量的画面量**（比例/落点/像素位置），
> 不要留无来源的角度或距离常数。判据：换个人用尺子能量出来 → 合格；量不出 → 是猜。
