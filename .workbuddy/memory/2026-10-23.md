## 16:0x v2 场景合成（用户反馈「还原效果有点差」后重做）

用户否掉了 v1 的 AABB 纸片法。重写为 `数据/render_v2.py`，五个关键突破：

1. **战场是纯 2.5D 纸片拼装**，不是 mesh 场景
   - 442 个 MeshFilter 只有 5 个带 mesh 指针（那 5 个 vcount=0，是地面碰撞壳）
   - 所有物体 Transform 的 scale 恒为 `(s, s, 1.0)`，423/442 旋转是 identity
   - ⇒ 每个物体 = 1×1 单位 quad，尺寸/朝向全在 Transform 里；v1 用 AABB 当矩形**丢掉了旋转和真实对齐**
   - 贴图由 `RuntimeTextureInstanceSetter` 运行时按「物体名 = 贴图名」绑定
   - 已验证：贴图 alpha bbox 宽高比 与 AABB 宽高比**完全一致**（0.56/0.56、12.57/12.57…）

2. **地形是缓上坡，不是平面**
   - 按 z 分桶取物体底边 y 的 15% 分位 → z:2.5~67.5 对应 y:-2.44~+7.06
   - 之前用单一 GROUND_Y=-2.34 导致远景树"浮空 3.5 米"
   - `height_curve()` 必须**强制单调不减**，否则凹陷会让求交跳到另一分支产生硬横带

3. **地平线附近求交必须二分，不能迭代**
   - 逐行反投影时 `den = sin(pitch) - k·cos(pitch)` 在地平线附近趋 0
   - 简单迭代在 dz=57 与 dz=-0.6 之间振荡 → 画面一条 delta=26.7 的硬线
   - `solve_dz()` 用 26 次二分求根，跳变降到 4.4

4. **相机必须支持 yaw**
   - 002 的最佳朝向是 +56.5°，固定朝前渲染时 19 段命中物全在画面右侧外（x 1700~2450）
   - 加 yaw 后 `xc = dx·cos - dz·sin`，`fh = dx·sin + dz·cos`
   - 相机位置 = 角色位置 - 13.5·(sin θ, 0, cos θ)，这样角色在画面正下方中央

5. **画面合成细节**
   - 天空用 skybox_side 按仰角→球面 v 映射（v=0.5 是地平线），雾色取地平线上方 24 行的均值
   - 地面用 ground01_c 按 `u = X/TILE mod 1`、`v = log(dist)` 做透视 tile + 4 级 mip
   - **ground01_c 顶部 13% 是亮雾边**，映射要从 VTOP=0.13 开始，否则地平线一条亮带
   - 雾要线性不能指数（指数会把 z=20~40 的前景吃掉变白块）；物体雾再乘 0.78
   - 贴地纸片底部 16% alpha 渐隐，消除坡上一排齐刷刷的切边
   - 超大纸片（>画面 10%）alpha 压到 0.28，否则 004 中间糊成一块浅色板
   - post：暗角 + 降饱和 0.79 + 青绿偏移 + bloom

**标注层** `数据/annotate_v2.py`：
- 命中物**按自身贴图 alpha 轮廓提亮**（不是矩形！矩形会变成大亮块）
- 穿透光带 + 刻度点；前 3 个目标画角括号 + 编号，其余只留点
- 数据卡 / 图例 / 标题条

**页面** `数据/gen_page_v2.py` → `H36-35充能点位标注.html`（5 战场 × 5 候选点位表）

**踩坑**：
- 名字前缀不一致：scan 里是 `dn_rock08_h`，props 里是 `sbg_swamplandjungle_dn_rock08_h` → 必须 short() 后比较
- HTML 里 CSS 的 `%` 会和 `%` 格式化冲突 → 改用 `__SECTIONS__` 占位 + replace
- 超大贴片过滤阈值从 22% 降到收紧 alpha 而非跳过，避免丢地形

## 14:50 战场还原 v3：改用原生装配参数 + three.js（推翻 v2 的 AABB 方案）

**触发**：用户指出「拼装出来的地图跟实际看到的差很多」，要求按游戏内装配参数还原，并指定
「找个开源项目直接整，不用自己搭」。

**调研结论**：用户给的两个站点都没有场景能力 —— nikke-db/visualiser 是 Spine 立绘查看器，
blablalink/shiftyspad 是官方小游戏页。没有现成的 NIKKE 场景还原开源项目。

**方案**：UnityPy 解析 → build_assembly.py 导出装配 JSON → export_glb.py 生成 glTF 2.0 →
three.js 渲染（KHR_materials_unlit，不引入 tone mapping）。渲染交给成熟开源引擎，只做格式转换。

**关键实证（推翻了三个旧假设）**：
- 相机 FOV = **60**（不是 40），near 0.1 / far 300，来自 spotpresentationbase_assets_spotcameracontrol
  的 Camera 组件。位置/俯仰 bundle 内没有（运行时 Cinemachine 驱动）。
- 后处理真值（fieldetc-map_assets_pp_field_swamplandjungle 的 VolumeProfile）：
  Bloom 0.9/0.7、Vignette 0.431/0.39、ColorAdjustments 对比+6/饱和+5/exposure+0.03/暖色滤镜。
  **不是**之前以为的「降饱和 + 青绿偏移」。
- 战场**不是视差卷轴**：SpotSingleMap 的 Near/Mid/Far/End 四层 _objectList 完全相同，IsOnScroll=0。
- burst_energy_max = **1,000,000**（ConfigBattleTable），社区流传的 10000 是缩小 100 倍的口径，
  百分比/发数结论不变。

**几何真相**：
- 所有 mesh 都是 0.5 厚平板（168/168 个 z 仅取 {0,0.5}），顶点沿 alpha 轮廓切边，非矩形 quad。
- 原生 mesh 无 UV（m_VertexData 只有 ch0 position，stride=12）→ UV 按正面局部包围盒生成，
  再按贴图 alpha bbox 收缩。
- MeshFilter.m_Mesh 恒为 0（运行时注入）；须取 MeshCollider.m_Mesh，兜底按「物体名==mesh名」。
- 贴图精确绑定：RuntimeTextureInstanceSetter._sprite → Sprite.m_RD.texture，437/437 命中。
- Sprite.m_PixelsToUnits=100，世界尺寸 = rect/100 × Transform.scale（scale8 校验通过）。

## v10.5 可信度层：verify_px.py（蒙特卡洛扰动复核）
- 用户要求：多轮模拟核对点位、整理可靠算法、拟定算法调整方案、让用户知道每个点的可信度。
- **关键设计决断**：把误差分两层。随机误差（站位 0.30m / 枪口高 0.15m / 手抖 max(2,0.8R)px / 后坐 0.12° / 几何 1.5px）进蒙特卡洛影响可信度；系统性偏差（相机俯角 2°/朝向 0.8°/FOV 0.8°/相机位置 0.10m）只做 OAT 敏感性、报「漂移像素」，因为它错了是整张图一起偏（工具级失效），摊到单点会让评分失去区分度——早期版本正是这样，24 点全 D。
- 两种抖法：follow（固定世界坐标、重投影回扰动后的画面，答案=点本身好不好打）为主指标；pixel（固定像素）为对照；两者之差 = label_risk（8 图中位 50 分）。
- **必须过的自检**：sigma 全 0 时要逐点复现 scan 的标称值（本次 8 图前 5 点全部一致、误差 0）。这条写进文档当门槛，不过就别看分布。

## 机制澄清：耐久按伤害量（HP），充能按命中次数 —— 两套解耦
- 用户问「充能点耐久度是按受击次数还是伤害量」。查 `导出/ConfigBattleTable.json`（139 条 id/value）实证：
  - 耐久：`soft_object_hp=100` / `medium_object_hp=500` / `hard_object_hp=1000` / `cover_hp=8000`，且 `*_object_def` **全部为 0** ⇒ HP 制，按累计伤害扣，非次数计数。assembly prop 无逐对象 hp 字段，只有 group 档位（001: soft80/medium28/hard35/static145/noncol134/cover15/ground5）。
  - 充能：`ulti_gauge_shot_hit=4`（基础刻度，显示口径 10000=满条）→ ×角色「攻击充能」倍率（小红帽 2.80% = 70× = 280）。另有独立通道：`use_skill=200` / `skill_hit=100` / `sec=100` / `hurt=480` / `cover_hurt=0` / `empty_ammo=13` / `kill_m|e|c|b=960|1440|1920|2880`。
  - ⇒ **同一次命中：充能按「件数」结算，耐久按「伤害」扣减，互相独立**。穿透 N 件 = N×280 充能，与被穿物体掉多少血无关。
- **风险发现（未解）**：`hpdamage_limit=30` 从未被项目引用。若语义为「单次命中对物体 HP 的扣减上限 30」，则几发碎 = soft 4 / medium 17 / hard 34 / cover 267，三档才有区分度，且实践中退化回「按次数」。若语义不是这个，单发伤害（上万）远大于 1000 → 三档退化成一枪全碎 → `n_steady`（中+硬）口径不成立 → §16 可信度体系的地基要重做。
- **用户实战反馈是反证**：「部分受击点耐久很低，很容易就打碎了」——若全部一枪碎就不会有「部分」这一说，故三档确有区分度，支持「单次扣减有上限/伤害对物体被缩放」。
- 待验证：实机打 soft 数发看第几发碎（1 发碎=无上限；4 发碎=30 上限）；查 ObjectTable/伤害公式；`groupshot_hp=300/time=600/max_gauge=300/gain_gauge=100` 疑似另一条「集火槽」通道，未查。

## v11 战场轮换算法（sim_charge.py）：从「单点段数」到「最大覆盖」
- 由「耐久怎么判定」引出：受击物碎掉即从场景消失，且**跨点位共享**（A 打碎的件 B 打不到）。第一次按「单点充满」建模直接撞上：A 假设下 shots=1 就停、charge 仅 16.8% —— 单点永远充不满，被迫改成战场级轮换模型。
- 两种假设（hpdamage_limit 是否生效）：A 一枪碎→每点只能用 1 发、需轮换 10~19 个点；B 上限 30→单点撑 17~34 发、一个点打到底。**玩法完全相反**。做法：两个都算、取较差者排序（稳健优化），区间都展示。
- **新指标「池」**：所有点位命中集合的并集 × 280 = A 模式下靠打地形能拿到的上限。8 图中只有 001(106%)/002(151%)/mw003(101%) 够充满；004 仅 36%、mw001 64%、005 64%、003 98%、mw002 98% —— 打光所有点也不够。⇒「打一轮没充能了」不是找错点，是目标总量不够，剩下靠打敌人。
- **覆盖率 11%~57%**（001：38/143；母鲸 35%~57%）：大量场景目标从未被任何点位打到。证实「点位挤中线」的代价 —— 决定池子的是**方向多样性**，不是点数。
- 算法升级：排序目标从「单点段数最大」→「边际覆盖最大」（max coverage 贪心，1-1/e）。002 省 4 发(-31%)、mw001/mw003 各省 2 发；Top1 不变（第一轮即新鲜件最多者）。A 模式下总充能 = 池×280 与顺序无关，但「充满消耗几个点」与顺序有关。
- 射速旁证：field_*_fire_speed_rate 按「间隔秒」解释，六武器折算全吻合实机手感；换弹时间无表 → 只报发数，秒数仅参考。
